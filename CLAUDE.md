# KWin MCP development

Follow [AGENTS.md](AGENTS.md) for repository commands, style, and real-system test requirements.

`kwin-mcp` serves MCP over stdio. Every `session_start` call creates a new isolated KWin session with its own `session_id`, so one server process can own several; a session's start, stop, and shutdown share a lifecycle gate. Startup resources remain owned until the `Session` is published, so cancellation can reap bwrap, D-Bus proxies, and the optional viewer. With `--autoclean`, workdir ownership ends only after removal succeeds.

Nothing that reads or deletes host files runs before the MCP handshake: the `--autoclean` startup sweeps have a thread of their own (`sweep_at_startup`), so `initialize` does not wait for another server's leftovers. A server that exits calls `begin_shutdown` with the cause before it stops anything. `signal_sender` records who sent SIGTERM, SIGINT or SIGHUP in the handler itself (`si_pid` and the sender's `/proc/<pid>/comm`; a sender such as pkill is gone a moment later), `SessionRouter::call_tool` answers every running and later call except a start or stop under way with `server_shutting_down`, `SessionStdio::answered` and `ControlCalls::idle` wait up to a second for those answers to be written, and the cause becomes the `detail` of the lifecycle record of each session stopped. A sandbox that ends by itself is diagnosed in `check_liveness` before teardown removes its log: `sandbox_exit_evidence` reads the compositor's exit file and the log tail into the death record, and `sandbox_exit_summary` says which ended first. pasta exits 0 on SIGTERM, so status 0 with `kwin_wayland` still running means an outside termination. `session_stop` answers within `SESSION_STOP_LIMIT`: `begin_stop` runs the graceful stages (`close_session_apps`, each bounded) until `STOP_FORCED_RESERVE` is left, then `teardown` and the workdir removal on a blocking thread whose stage `StopProgress` names; past the limit the answer is `cleanup_pending` and the `PendingStop` stays with the handle for the next stop or for shutdown. A re-execution pauses `ControlCalls` so forwarded calls finish before the exec, and `forward_session_call_checked` retries its connection while the owner is running.

Bubblewrap mounts the host root read-only and gives the container an overlay for `$HOME`. KWin runs on a virtual output. EIS supplies input, KWin D-Bus supplies window and screenshot operations, and AT-SPI supplies accessibility data. Mouse and screenshot coordinates are relative to the active window. `screenshot` uses `CaptureScreen("Virtual-0")` so popups composite into the frame, then crops to the active window by default; a `region` may extend past the window, and the metadata reports the window and the window-relative region the image covers.

`launch_app` runs a shell expression. A PATH directory scoped to that launch wraps known Chromium-family executable names. The wrapper adds missing Wayland, KWallet, and renderer-accessibility switches to the browser's argv, and for browsers `--no-first-run` and `--no-default-browser-check`, so a fresh profile opens the requested URL instead of Chrome's first-run terms page. It assigns Chromium-family programs the session's forwarded CDP port, replacing any caller-supplied `--remote-debugging-port`. A successful connection returns `cdp_port`; `launch_app` `cdp: false` passes the wrapper no port (the port is forwarded to the host's loopback without authentication, so any program of the user can drive that browser). Google Chrome and Edge refuse the port on their default data directory, which they recognise by comparing the directory they run on, resolved, with the unresolved path `$CHROME_CONFIG_HOME/<name>` as text (Chromium, Brave and Vivaldi have no such check). So for `google-chrome`, `google-chrome-stable`, `microsoft-edge`, `microsoft-edge-stable` and `msedge` without a `--user-data-dir`, the wrapper (`prepare_default_profile`) resolves the real directory `${CHROME_CONFIG_HOME:-${XDG_CONFIG_HOME:-$HOME/.config}}/<name>`, exports `CHROME_CONFIG_HOME` for the browser process alone as a mirror of that config home under the workdir's `browser-config` (`BROWSER_CONFIG_STORE`), in which every `BROWSER_CONFIG_DIRS` name that exists, and the browser's own, is a symlink to the real directory, and passes the real path as `--user-data-dir`. The browser runs on the directory a plain launch opens (same `SingletonLock`, cookies, profiles; `prepare_browser_cookies`, `mark_browser_exits_clean` and `hide_browser_sessions` apply to it as before), a launch that bypasses the wrapper hands off to it, and a browser it starts inherits the variable and lands on the real directories through the links. A `--user-data-dir` that a distribution launcher adds from its flags file (the wrapper reads the `*flags.conf` name out of the launcher script, since those switches come ahead of its own) counts as the directory the browser runs on: it is not added a second time, and one that names another directory is left alone. A program named `chrome` may be Chrome for Testing with another default and gets no port without its own `--user-data-dir`. The wrapper's marker file tells `launch_app` which way the port was given (`DefaultProfilePort`); when the connection fails and the session log holds the browser's "requires a non-default data directory", `launch_app` reports `cdp_refused` and writes `browser-config/unlinked`, after which the wrapper gives the browser a default with no profile in it instead of the link. Bash handles compound commands and `nohup` or `timeout` wrappers. Absolute executable paths bypass the PATH wrapper, so callers using them must supply their own flags.

`launch_app` without `session_id` on a router that uses no session (`SessionRouter::launch`) runs `session_start` with defaults first and adds `session_id`, `session_started` and `session` to the result; `viewer: true` is handled there too and never reaches the session's tool. The shell that runs a launch script has `KWIN_MCP_LAUNCH=<id>-<nanoseconds>` in its environment. `sandbox_processes` reads `/proc/<sandbox>/root/proc`, and `process_launch` names a process's launch from its own environment or its nearest ancestor's: Chromium overwrites its environment image when it sets its process title, so the browser process is found through the script's shell, which lives as long as the command. At the deadline, a command still running without a window is `slow_start` when its processes used CPU during the two-second grace sample and `window_not_observed` when they were idle; it is then kept in the session's `LaunchLedger` (`KwinMcp::launches`) for ten minutes or until its processes are gone. `LaunchLedger::settle`, run by `window_list` and by every `launch_app`, credits a window mapped since such a launch's baseline to it by process (or, for a process that names no launch, by timing to the oldest waiting launch); a waiting `launch_app` leaves a window of an earlier waiting launch alone unless its own command exited 0. A browser command that exited 0 with no new window and no lasting title change is settled after three seconds by `HandoffEvidence::target`; a second start of another single-instance application by `running_instance_window`. The ledger is not part of the reload state. Launched applications use the session's private D-Bus bus through an unfiltered proxy, so they can own names; nothing is activated on that bus.

FUSE: `fusermount` binaries are setuid and cannot work under `no_new_privs` in a user namespace, and bwrap nests a second user namespace for `--uid` != 0 (devpts needs root), where capabilities cannot mount. When the host supports it (`/dev/fuse`, non-setuid bwrap, `setpriv`, `fusermount`), bwrap runs at uid 0 with `CAP_SYS_ADMIN` in one namespace; `kwin-mcp --fuse-helper` alone keeps it, and the entrypoint runs everything else through `unshare --user --map-user=<uid>` and `setpriv` with no capabilities. Sandbox `fusermount`/`fusermount3` are this binary acting as shims (see `src/fuse_bridge.rs`); the helper runs the real ones only to mount on user-owned directories or unmount FUSE mounts.

A session's process tree is `systemd-run --scope` → `prlimit` → `pasta [options] -- bwrap`. A server that inherited `no_new_privs` (any parent inside a bwrap-based sandbox) starts `kwin-mcp --netns-holder` in pasta's place instead, in the same scope with the same options: `src/netns_holder.rs` says why pasta cannot start bwrap there and how the holder does. Its children are bwrap and an attached pasta, so code that walks the tree must not assume the top process has one child.

The container reaches the host KWallet through a filtered D-Bus proxy whose upstream is a private bus where `src/wallet_mediator.rs` owns `org.kde.kwalletd6`. KWallet 6's kwalletd creates a collection when `open` names one its provider does not list, never releases handles when a client disconnects, and ignores `close(handle, false)`. The mediator forwards read-only calls, allows `open` only for the host's network wallet when kwalletd lists it and its Secret Service collection is unlocked (otherwise it answers as a disabled wallet or -1), turns the session's `close` into a forced release of its own handle, denies writes and whole-wallet close, and force-closes every remaining handle at teardown. `session_start` reports `wallet.forwarding` and the reason. The server itself never opens or snapshots the wallet. `session_start` enables `org.a11y.Status.IsEnabled`; renderer accessibility exposes Chrome web content to AT-SPI even when CDP is unavailable.

The same private bus carries a session-local Secret Service (`src/secret_service.rs`, `org.freedesktop.secrets`), which session applications reach on that bus like the wallet. `session_start` copies the unlocked collections of the host's Secret Service once, read-only (`OpenSession("plain")`, property reads, `GetSecrets`, `Session.Close`, sequentially, NoAutoStart, never `Unlock`), and keeps a connection with an unanswered request open for the life of the server, because gnome-keyring exits when a client vanishes mid-request (#156). Session writes stay in the copy; the `default` alias always resolves; `session_start` reports `secrets`. `KWIN_MCP_SECRET_SERVICE_ADDRESS` reads the host side from another bus (the e2e fixture).

pasta forwards no TCP port from the session to the host (`--tcp-ns none`): its `auto` forwarding offers every host port on both loopback families and resets a connection it cannot deliver, so `localhost` to an IPv4-only host server failed most of the time (#782, #862). `src/loopback_forward.rs` does it instead, as two processes of this binary per session: `--loopback-forwarder TOP_PID CDP_PORT` on the host (given pasta or, under no_new_privs, the namespace holder) lists `/proc/net/tcp` and `/proc/net/tcp6` every 250 ms and copies bytes, and its child `--loopback-sockets PID` enters the user and network namespaces of the top process's child that is in another network namespace (single-threaded, before any runtime) only to make listening sockets on `127.0.0.1` or `::1`, which it passes back with `SCM_RIGHTS`. A port is offered only in the families the host accepts it on. UDP stays with pasta.

A host graphical socket beneath HOME is made absent in the session by a whiteout (a 0:0 character device) in the overlay upper layer (`OverlayPlan::hide_host_socket`), so single-instance applications start their own instance; `/dev/null` masks remain only where no upper layer exists. `/run/avahi-daemon/socket` is bound read-only for nss-mdns. `src/ui_names.rs` holds the text and role comparison shared by `accessibility_tree` and the element search, and `SeenNames`, which lets a search reach an AT-SPI object by a name it was reported under before the page renamed it.

The HOME overlay's lower layer is the live host HOME. SQLite databases a host process holds open in WAL mode (found through `/proc/*/fd` `-wal` descriptors) normally resolve through read-only directory aliases so database and sidecar reads use the host inodes and locks. Explicit `session_start.host_write_paths` bind existing application state directories beneath HOME writable instead, bypassing staging copies and the read-only SQLite aliases. For Codex/ChatGPT desktop, pass the absolute path to `~/.codex`; its writes then persist in the real host state. Existing host Unix sockets in shared directories remain blocked. The response, session list and reload state retain the selected paths.

The runtime workdir lives on `/tmp`, which systemd mounts as tmpfs with a per-user quota (about 80% of its size), so EDQUOT can occur while `df` shows free space. The HOME overlay and temporary KWin scripts live in the session's disk twin. The script directory is mounted read-only under the sandbox runtime directory, so window inspection and inline screenshots do not need space on `/tmp`. `screenshot` writes the PNG atomically, never leaves a partial or stale PNG, and reports a recoverable `write_failed` error with quota numbers if saving fails. Retry with `inline=true` to receive the captured image with `path: null` and `write_error`. Sessions restored from older servers retain their old script storage until recreated.

`browser_navigate` never takes a window title as proof of a page. Chrome hands ctrl+l to the page before acting on it, so a busy page delays it and a page that handles it keeps it: text typed after a fixed wait lands in the page or reaches the address bar without its beginning. With CDP the tool sends `Page.navigate` to the tab's target on a WebSocket of its own (chromiumoxide withholds that method's answer until the frame's load events, which a download, an error page and an aborted navigation never send) and reads the tab's committed entry back; the tab is the one target whose title the window's caption carries, in the browser whose PID is the window's. Without CDP `src/browser_address.rs` binds the window's AT-SPI frame, its address bar (class `OmniboxViewViews`), tab list and showing document before anything is sent: the bar is focused with `Component.GrabFocus`, the address is typed or pasted (the agent's selection is lent and taken back through `ClipboardStore`), Return follows only when the bar's text equals the address, and the landing is the document's `URI` attribute with the selected tab unchanged. A navigation replaces the document object even when the address stays the same. An address always gets a scheme first, because the bar decides between an address and a search by the text's shape.

Chrome's file chooser is its own in-process GTK4 dialog, not the portal. For a file upload, Enter in its location bar cancels the dialog (the input's `cancel` event fires, nothing attaches) while zenity's GTK4 chooser accepts the same injected keys, so the file-upload sequence is Ctrl+L, absolute file path, Alt+O (the Open mnemonic). For `chrome://extensions` → **Load unpacked**, use Ctrl+L and an absolute extension directory visible inside the session, inspect the path, then click the chooser's top-right **Open**. Bottom **Select Folder** chooses the dialog mode; it does not accept the directory. Verify the extension card appears after accepting; a closed chooser or toast alone does not establish activation. See [the folder-selection procedure](README.md#chrome-load-unpacked) for path, typing-receipt, and launch-flag checks. The save dialog (ctrl+s) is the same dialog: it opens with only the stem of the suggested name selected, Return in its name field does not accept it (Alt+S, the Save mnemonic, does; zenity's chooser accepts the same Return), and since it shows AT-SPI nothing, `TextReceipt::discover` ends in `NoAccessibleFocus`. `keyboard_type replace=true` sends ctrl+a without a readable field in two cases only: `UnreadableFocus` (focused, editable, unreadable) and `NoAccessibleFocus` in a transient or dialog window; the result then says the selection was not checked. A main window that shows accessibility nothing may be a terminal, where ctrl+a is not select-all, so it stays refused.

A link's target is reported by both element tools and must be the same value in each: `find_ui_dom.js` reads the element's resolved `href` property for the `cdp` backend, `atspi_link_target` reads `Hyperlink.GetURI(0)` (Chrome publishes it resolved and has no target in the object attributes), and the CDP tree reads the AX node's `url` property. `find_ui_elements` returns it as `href` (not in `compact`), `accessibility_tree` only with `show_links=true` as a last row field `href=`, cut in the middle past `A11Y_HREF_MAX_CHARS` by `cut_middle`, the rule of long names. `LevelTree` returns whole levels within `A11Y_TREE_MAX_CHARS`; the one level that may be returned in part is `paged_level` (the first, or the one below a `root=ID`), a page of rows at a time with `+N more rows offset=K`, because a `role` filter lifts every match to one level and a results page has hundreds of links. `browser_read` (`src/page_read.js`) returns the text, outer HTML or links of the active tab's top document through CDP, sliced in the page so at most `PAGE_READ_MAX_CHARS` cross the socket; it picks its tab as `browser_navigate` does (`cdp_is_process`, `cdp_active_tab`), refuses with `cdp_unavailable` when the session has no connection, and reads the DOM only: no cookies, no storage, no field values, and no `value` attribute of a password field in the HTML.

`accessibility_tree` is the window tree unless the caller asks for the page: callers read the browser frame, tab strip and toolbar from it and match AT-SPI role names, so an open CDP port must not change what it returns (#951). `source=page`, or a `root` that is a page node ID (no `/`), reads the CDP tree of the one tab the active window shows (`active_browser_page`, shared with `browser_read`), never another tab of the connected browser.

The session `workdir` (returned as `host_shared_dir`) is bind-mounted at the same absolute path in the session and on the host; host-facing sockets, FIFOs, logs, and output belong there. Outside it and explicitly shared `host_write_paths`, session writes never reach the host on their own. `wait_for_file` can observe an asynchronously produced artifact until its inode, size, and modification time remain unchanged for a bounded interval; this does not prove its producer exited. `export_file` reads a session path through `/proc/<bwrap child>/root` (so both HOME overlay files and the private `/tmp` work), copies it to a host path via a temporary file and rename, and compares it byte for byte; it refuses to overwrite unless asked and reports downloads still in progress.

Host additions/edits are not reliably synchronized into a running HOME overlay: private copies, whiteouts, split-mount staging and application caches can hide them. `import_file` explicitly refreshes one file through the session's mounted filesystem, verifies the bytes before atomic replacement, and requires `overwrite=true` for an existing session file. It resolves destination parent symlinks inside the sandbox root with `openat2(RESOLVE_IN_ROOT | RESOLVE_NO_MAGICLINKS)` and pins that directory descriptor. Reopen/reload the file in the application afterward; the tool does not update application caches or unsaved buffers.

The optional host viewer writes `viewer-status.json` in the workdir; `session_start` and `viewer_open` report its outcome (ready after the host renderer successfully submits the first PipeWire frame for presentation, starting, unavailable with a reason, disabled) without failing the session. Readiness reports render submission, not compositor acknowledgement. KWin connects to `$XDG_RUNTIME_DIR/pipewire-0` as it starts, before the session's own PipeWire is up, and the viewer reads the daemon at that path: a host socket linked there puts the screencast node into the host's graph and the session manager answers the viewer "no target node available". So `session_start` never links the host runtime directory's `pipewire-0`, `pipewire-0-manager` or `pulse` (`HOST_MEDIA_ENTRIES`; systemd alone holds a socket-activated one, so no desktop process marks it), and links no host socket at all when most of the user's processes refuse to show their descriptors (`descriptors_hidden`: a launcher that confined the server with Landlock or a user namespace), because nothing can then tell a desktop socket from a helper. The viewer lists the daemon's nodes before it connects its stream and fails at once, with that cause, when the compositor's node is not among them; a stream PipeWire puts in the error state ends the viewer with PipeWire's message instead of a first-frame timeout. `viewer_close` for a session that ended (a terminal handle, a lifecycle record, or an owning server that is no longer running) answers `already_closed` with that `session_status`. Teardown waits up to 5 s (`SCOPE_EXIT_WAIT`) for killed processes to leave the session's scope, kills the cgroup once more, and `session_stop` reports the ones still there as `processes_exiting` with their state, kernel wait and the host's disk pressure: a process in state D on a saturated disk ends by itself and is not a leak. The window redraws on the compositor's frame callbacks; a compositor that is not showing it (minimized, another virtual desktop, outputs powered off) sends none, so the viewer draws a frame that has waited 100 ms itself, through a mailbox swapchain that never waits for the previous present, and counts those presents apart (`presented_unshown`). The session clipboard belongs to the agent and the host clipboard to the viewer's user: the viewer watches both through `ext_data_control_v1`, sends a copy or cut made with a viewer shortcut to the host, pastes the host clipboard for a viewer paste shortcut, and then restores the agent's selection. The session's half of that handoff is `SessionClipboard` in `src/bin/kwin-viewer.rs`, shared by the local viewer and the remote frame sender. The host clipboard is always the one of the desktop the viewer window is on, which is the desktop of the server that received the call.

For remote MCP use, set the client's stdio command to SSH and run `kwin-mcp --no-viewer` on the remote host. SSH carries MCP messages. Alternatively `kwin-mcp --listen ADDRESS[:PORT]` on a machine serves other machines' servers over WebSocket (`src/remote.rs`; shared secret in `~/.config/kwin-mcp/remote-secret`), and `session_start` `host` starts a session there: the local `SessionRouter` forwards every call with that ID over the socket, and the listener gives each connection its own router, whose sessions it shuts down when the connection ends. A server that re-executes itself keeps those connections, and the listener is not involved: `RemoteSessions::hold` waits out every request to a listener, `remote::Handover::hold` stops each control socket once its byte counts show no part of a WebSocket message in the library's buffers, the socket's descriptor is inherited through the reload state together with the session-to-host map and the viewer PIDs, and `remote::adopt_control` continues on it without a handshake. The descriptor loses close-on-exec only in the exec call's `pre_exec`, and only when the target binary contains `remote::ADOPTS_CONTROL_MARK`, because a child or an older build holding the socket would keep sessions alive that nobody reaches; a server that dies hands nothing over, so its sessions still end at once. `viewer_open` on such a session opens the window on the caller's machine: the local router starts `kwin-viewer --stream`, which opens a second WebSocket (`/frames`, same secret) with a one-time ticket, and forwards `viewer_open` with that ticket on the control socket; the listener's `FrameSockets` pairs the two and hands the socket as stdin to `kwin-viewer --stream-serve` beside the session, which is that session's `viewer_child`. `src/viewer_stream.rs` holds the wire format and the sender's decisions, which put colour accuracy first and have no frame-rate target: a frame only when the pixels changed, the newest capture only and one frame on its way at a time, area-scaled to the viewer's reported drawable size, on a socket the kernel paces inside a budget of 90% of the link speed (`--link-mbps` overrides the speed, loopback is unlimited). The streams that leave a listener on one interface share that budget (`src/links.rs`): the frame senders are separate processes, so `FrameSockets` owns a `LinkScheduler` with one `links::Shares` per interface, and each sender's standard output is its socket to it (a sender without one, under an older listener, has the whole budget). A sender writes `Report::Wire` when a frame goes onto the wire and when its last byte has left, and reads a `Grant` whenever anything changed: `pace`, the budget divided among the streams on the wire at that moment, which its `link-share` thread applies to the socket at once (so the paces add up to the budget, an idle stream's part is taken over immediately and a stream alone has everything), and `share`, the budget divided among the streams that send frames in a row (from the second frame within 250 ms of the one before until 250 ms after the last), which goes to `ModeControl::share` and scales its measured link speed, so one frame of another viewer does not change a mode and a second scrolling viewer does. `Notice::Share` tells the viewer. On the caller's side `kwin-viewer --stream` chooses its path when its machine has several interfaces that reach the listener (`links::paths_to`, `links::choose`: the largest fair share, wired first, a wireless path only when it gives more than a fair share of the wire; the user's open stream viewers are counted in `links::Registry` under `$XDG_RUNTIME_DIR/kwin-mcp-streams`), binds the frame socket to that path's address and, with `SO_BINDTODEVICE` (unprivileged since Linux 5.7), to its interface before connecting (`remote::connect_frames` with a `Source`; the routing table's own path is not bound), and reports a bound path's usable speed with `Request::Path`, which caps its grant. A stream never changes path while its path works. When the path dies (its interface leaves the usable paths, or the socket times out or loses its route, while another path exists; a close or reset from the session's machine is not that), the viewer asks the server that started it for a ticket on `links::RECONNECT_SOCKET` beside its log (`RemoteSessions::serve_reconnects`, same user only, re-bound after a reload), opens a frame socket on another path, and the forwarded `viewer_open` with that ticket replaces the frame sender; the window and its picture stay, and its writer task repeats the drawable size and the presentation notice on the new socket. `links::PATH_FILE` beside the viewer's log holds the path and share that `viewer_open` returns as `viewer.path`; `KWIN_VIEWER_STREAM_PATHS` lists paths in place of the interfaces for tests. `ModeControl` sends raw RGB, the session's exact pixels, while the measured link carries a frame within 100 ms; it sends DSC only when raw is slower than that and DSC, with its measured encode time, arrives at least a quarter sooner, at the highest whole rate from 6 to 12 bpp the link carries in 100 ms (the rate follows the link, never the CPU), and a change of mode or rate needs 4 frames in a row. `Settle` sends a still DSC frame once more raw after 150 ms, and the viewer presents through a UNORM sRGB swapchain without conversion, so a still screen is pixel-exact. Viewer input returns on the frame socket; screenshots and all tool calls stay on the control socket. The remote viewer bridges the clipboard over the same frame socket: `--stream` owns the host half (the caller's desktop clipboard) and `--stream-serve` the session half. A paste shortcut sends `Request::ClipboardPaste` with the caller's clipboard text ahead of the key record, a copy or cut shortcut sends `Request::ClipboardCopy` and the sender answers with `Notice::Clipboard` once the session's selection changed; the sender handles each request before it reads the next record, and restores the agent's selection afterwards. These are JSON text messages carrying UTF-8 text of at most 1 MiB (`CLIPBOARD_TEXT_BYTES`; longer or non-text selections are refused whole, and a refused paste inserts nothing rather than the agent's selection). The sender announces the bridge in `hello` (`clipboard_text_bytes`), a viewer sends requests only to a sender that did, older senders ignore text messages and both ends ignore unknown text types, so either end may be older. `ClipText` has no `Display` and a redacted `Debug`, and `Request::decode`/`Notice::decode` never report the parser's message, so clipboard text reaches no log. The frame socket is plain `ws://`: clipboard text crosses the LAN unencrypted. A frame socket is bound to one session by its ticket and to one window, a viewer accepts a `clipboard` text only as the answer to its own last copy request, and the sender never answers with a selection that carries the generated-secret marker, so a viewer bridges its own session only. `clipboard_write target=host` for a remote session is carried out by the calling server's `SessionRouter::write_callers_clipboard` and never forwarded: text and generated secrets are made and written on the caller's machine and cross the network only in a viewer paste. `target=session` is forwarded, and a secret for it is generated by the listener on the session's machine, so only its parameters and its length cross the control socket. A listener refuses `target=host` from a peer. The capture ends with either socket. The remote host needs KDE, bubblewrap, render and input devices, and an active user D-Bus.
