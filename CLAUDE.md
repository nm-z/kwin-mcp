# KWin MCP development

Follow [AGENTS.md](AGENTS.md) for repository commands, style, and real-system test requirements.

`kwin-mcp` serves MCP over stdio. Every `session_start` call creates a new isolated KWin session with its own `session_id`, so one server process can own several; a session's start, stop, and shutdown share a lifecycle gate. Startup resources remain owned until the `Session` is published, so cancellation can reap bwrap, D-Bus proxies, and the optional viewer. With `--autoclean`, workdir ownership ends only after removal succeeds.

Bubblewrap mounts the host root read-only and gives the container an overlay for `$HOME`. KWin runs on a virtual output. EIS supplies input, KWin D-Bus supplies window and screenshot operations, and AT-SPI supplies accessibility data. Mouse and screenshot coordinates are relative to the active window. `screenshot` uses `CaptureScreen("Virtual-0")` so popups composite into the frame, then crops to the active window by default; a `region` may extend past the window, and the metadata reports the window and the window-relative region the image covers.

`launch_app` runs a shell expression. A PATH directory scoped to that launch wraps known Chromium-family executable names. The wrapper adds missing Wayland, KWallet, and renderer-accessibility switches to the browser's argv, and for browsers `--no-first-run` and `--no-default-browser-check`, so a fresh profile opens the requested URL instead of Chrome's first-run terms page. It assigns Chromium-family programs the session's forwarded CDP port, replacing any caller-supplied `--remote-debugging-port`; Google Chrome and Edge need a non-default `--user-data-dir` for CDP. A successful connection returns `cdp_port`. Bash handles compound commands and `nohup` or `timeout` wrappers. Absolute executable paths bypass the PATH wrapper, so callers using them must supply their own flags.

`launch_app` without `session_id` on a router that uses no session (`SessionRouter::launch`) runs `session_start` with defaults first and adds `session_id`, `session_started` and `session` to the result; `viewer: true` is handled there too and never reaches the session's tool. The shell that runs a launch script has `KWIN_MCP_LAUNCH=<id>-<nanoseconds>` in its environment. `sandbox_processes` reads `/proc/<sandbox>/root/proc`, and `process_launch` names a process's launch from its own environment or its nearest ancestor's: Chromium overwrites its environment image when it sets its process title, so the browser process is found through the script's shell, which lives as long as the command. At the deadline, a command still running without a window is `slow_start` when its processes used CPU during the two-second grace sample and `window_not_observed` when they were idle; it is then kept in the session's `LaunchLedger` (`KwinMcp::launches`) for ten minutes or until its processes are gone. `LaunchLedger::settle`, run by `window_list` and by every `launch_app`, credits a window mapped since such a launch's baseline to it by process (or, for a process that names no launch, by timing to the oldest waiting launch); a waiting `launch_app` leaves a window of an earlier waiting launch alone unless its own command exited 0. A browser command that exited 0 with no new window and no lasting title change is settled after three seconds by `HandoffEvidence::target`; a second start of another single-instance application by `running_instance_window`. The ledger is not part of the reload state. Launched applications use the session's private D-Bus bus through an unfiltered proxy, so they can own names; nothing is activated on that bus.

FUSE: `fusermount` binaries are setuid and cannot work under `no_new_privs` in a user namespace, and bwrap nests a second user namespace for `--uid` != 0 (devpts needs root), where capabilities cannot mount. When the host supports it (`/dev/fuse`, non-setuid bwrap, `setpriv`, `fusermount`), bwrap runs at uid 0 with `CAP_SYS_ADMIN` in one namespace; `kwin-mcp --fuse-helper` alone keeps it, and the entrypoint runs everything else through `unshare --user --map-user=<uid>` and `setpriv` with no capabilities. Sandbox `fusermount`/`fusermount3` are this binary acting as shims (see `src/fuse_bridge.rs`); the helper runs the real ones only to mount on user-owned directories or unmount FUSE mounts.

A session's process tree is `systemd-run --scope` → `prlimit` → `pasta [options] -- bwrap`. A server that inherited `no_new_privs` (any parent inside a bwrap-based sandbox) starts `kwin-mcp --netns-holder` in pasta's place instead, in the same scope with the same options: `src/netns_holder.rs` says why pasta cannot start bwrap there and how the holder does. Its children are bwrap and an attached pasta, so code that walks the tree must not assume the top process has one child.

The container reaches the host KWallet through a filtered D-Bus proxy whose upstream is a private bus where `src/wallet_mediator.rs` owns `org.kde.kwalletd6`. KWallet 6's kwalletd creates a collection when `open` names one its provider does not list, never releases handles when a client disconnects, and ignores `close(handle, false)`. The mediator forwards read-only calls, allows `open` only for the host's network wallet when kwalletd lists it and its Secret Service collection is unlocked (otherwise it answers as a disabled wallet or -1), turns the session's `close` into a forced release of its own handle, denies writes and whole-wallet close, and force-closes every remaining handle at teardown. `session_start` reports `wallet.forwarding` and the reason. The server itself never opens or snapshots the wallet. `session_start` enables `org.a11y.Status.IsEnabled`; renderer accessibility exposes Chrome web content to AT-SPI even when CDP is unavailable.

The same private bus carries a session-local Secret Service (`src/secret_service.rs`, `org.freedesktop.secrets`), which session applications reach on that bus like the wallet. `session_start` copies the unlocked collections of the host's Secret Service once, read-only (`OpenSession("plain")`, property reads, `GetSecrets`, `Session.Close`, sequentially, NoAutoStart, never `Unlock`), and keeps a connection with an unanswered request open for the life of the server, because gnome-keyring exits when a client vanishes mid-request (#156). Session writes stay in the copy; the `default` alias always resolves; `session_start` reports `secrets`. `KWIN_MCP_SECRET_SERVICE_ADDRESS` reads the host side from another bus (the e2e fixture).

pasta forwards no TCP port from the session to the host (`--tcp-ns none`): its `auto` forwarding offers every host port on both loopback families and resets a connection it cannot deliver, so `localhost` to an IPv4-only host server failed most of the time (#782, #862). `src/loopback_forward.rs` does it instead, as two processes of this binary per session: `--loopback-forwarder TOP_PID CDP_PORT` on the host (given pasta or, under no_new_privs, the namespace holder) lists `/proc/net/tcp` and `/proc/net/tcp6` every 250 ms and copies bytes, and its child `--loopback-sockets PID` enters the user and network namespaces of the top process's child that is in another network namespace (single-threaded, before any runtime) only to make listening sockets on `127.0.0.1` or `::1`, which it passes back with `SCM_RIGHTS`. A port is offered only in the families the host accepts it on. UDP stays with pasta.

A host graphical socket beneath HOME is made absent in the session by a whiteout (a 0:0 character device) in the overlay upper layer (`OverlayPlan::hide_host_socket`), so single-instance applications start their own instance; `/dev/null` masks remain only where no upper layer exists. `/run/avahi-daemon/socket` is bound read-only for nss-mdns. `src/ui_names.rs` holds the text and role comparison shared by `accessibility_tree` and the element search, and `SeenNames`, which lets a search reach an AT-SPI object by a name it was reported under before the page renamed it.

The HOME overlay's lower layer is the live host HOME. SQLite databases a host process holds open in WAL mode (found through `/proc/*/fd` `-wal` descriptors) normally resolve through read-only directory aliases so database and sidecar reads use the host inodes and locks. Explicit `session_start.host_write_paths` bind existing application state directories beneath HOME writable instead, bypassing staging copies and the read-only SQLite aliases. For Codex/ChatGPT desktop, pass the absolute path to `~/.codex`; its writes then persist in the real host state. Existing host Unix sockets in shared directories remain blocked. The response, session list and reload state retain the selected paths.

The runtime workdir lives on `/tmp`, which systemd mounts as tmpfs with a per-user quota (about 80% of its size), so EDQUOT can occur while `df` shows free space. The HOME overlay and temporary KWin scripts live in the session's disk twin. The script directory is mounted read-only under the sandbox runtime directory, so window inspection and inline screenshots do not need space on `/tmp`. `screenshot` writes the PNG atomically, never leaves a partial or stale PNG, and reports a recoverable `write_failed` error with quota numbers if saving fails. Retry with `inline=true` to receive the captured image with `path: null` and `write_error`. Sessions restored from older servers retain their old script storage until recreated.

`browser_navigate` never takes a window title as proof of a page. Chrome hands ctrl+l to the page before acting on it, so a busy page delays it and a page that handles it keeps it: text typed after a fixed wait lands in the page or reaches the address bar without its beginning. With CDP the tool sends `Page.navigate` to the tab's target on a WebSocket of its own (chromiumoxide withholds that method's answer until the frame's load events, which a download, an error page and an aborted navigation never send) and reads the tab's committed entry back; the tab is the one target whose title the window's caption carries, in the browser whose PID is the window's. Without CDP `src/browser_address.rs` binds the window's AT-SPI frame, its address bar (class `OmniboxViewViews`), tab list and showing document before anything is sent: the bar is focused with `Component.GrabFocus`, the address is typed or pasted (the agent's selection is lent and taken back through `ClipboardStore`), Return follows only when the bar's text equals the address, and the landing is the document's `URI` attribute with the selected tab unchanged. A navigation replaces the document object even when the address stays the same. An address always gets a scheme first, because the bar decides between an address and a search by the text's shape.

Chrome's file chooser is its own in-process GTK4 dialog, not the portal. For a file upload, Enter in its location bar cancels the dialog (the input's `cancel` event fires, nothing attaches) while zenity's GTK4 chooser accepts the same injected keys, so the file-upload sequence is Ctrl+L, absolute file path, Alt+O (the Open mnemonic). For `chrome://extensions` → **Load unpacked**, use Ctrl+L and an absolute extension directory visible inside the session, inspect the path, then click the chooser's top-right **Open**. Bottom **Select Folder** chooses the dialog mode; it does not accept the directory. Verify the extension card appears after accepting; a closed chooser or toast alone does not establish activation. See [the folder-selection procedure](README.md#chrome-load-unpacked) for path, typing-receipt, and launch-flag checks.

The session `workdir` (returned as `host_shared_dir`) is bind-mounted at the same absolute path in the session and on the host; host-facing sockets, FIFOs, logs, and output belong there. Outside it and explicitly shared `host_write_paths`, session writes never reach the host on their own. `wait_for_file` can observe an asynchronously produced artifact until its inode, size, and modification time remain unchanged for a bounded interval; this does not prove its producer exited. `export_file` reads a session path through `/proc/<bwrap child>/root` (so both HOME overlay files and the private `/tmp` work), copies it to a host path via a temporary file and rename, and compares it byte for byte; it refuses to overwrite unless asked and reports downloads still in progress.

Host additions/edits are not reliably synchronized into a running HOME overlay: private copies, whiteouts, split-mount staging and application caches can hide them. `import_file` explicitly refreshes one file through the session's mounted filesystem, verifies the bytes before atomic replacement, and requires `overwrite=true` for an existing session file. It resolves destination parent symlinks inside the sandbox root with `openat2(RESOLVE_IN_ROOT | RESOLVE_NO_MAGICLINKS)` and pins that directory descriptor. Reopen/reload the file in the application afterward; the tool does not update application caches or unsaved buffers.

The optional host viewer writes `viewer-status.json` in the workdir; `session_start` and `viewer_open` report its outcome (ready after the host renderer successfully submits the first PipeWire frame for presentation, starting, unavailable with a reason, disabled) without failing the session. Readiness reports render submission, not compositor acknowledgement. KWin connects to `$XDG_RUNTIME_DIR/pipewire-0` as it starts, before the session's own PipeWire is up, and the viewer reads the daemon at that path: a host socket linked there puts the screencast node into the host's graph and the session manager answers the viewer "no target node available". So `session_start` never links the host runtime directory's `pipewire-0`, `pipewire-0-manager` or `pulse` (`HOST_MEDIA_ENTRIES`; systemd alone holds a socket-activated one, so no desktop process marks it), and links no host socket at all when most of the user's processes refuse to show their descriptors (`descriptors_hidden`: a launcher that confined the server with Landlock or a user namespace), because nothing can then tell a desktop socket from a helper. The viewer lists the daemon's nodes before it connects its stream and fails at once, with that cause, when the compositor's node is not among them; a stream PipeWire puts in the error state ends the viewer with PipeWire's message instead of a first-frame timeout. `viewer_close` for a session that ended (a terminal handle, a lifecycle record, or an owning server that is no longer running) answers `already_closed` with that `session_status`. Teardown waits up to 5 s (`SCOPE_EXIT_WAIT`) for killed processes to leave the session's scope, kills the cgroup once more, and `session_stop` reports the ones still there as `processes_exiting` with their state, kernel wait and the host's disk pressure: a process in state D on a saturated disk ends by itself and is not a leak. The window redraws on the compositor's frame callbacks; a compositor that is not showing it (minimized, another virtual desktop, outputs powered off) sends none, so the viewer draws a frame that has waited 100 ms itself, through a mailbox swapchain that never waits for the previous present, and counts those presents apart (`presented_unshown`). The session clipboard belongs to the agent and the host clipboard to the viewer's user: the viewer watches both through `ext_data_control_v1`, sends a copy or cut made with a viewer shortcut to the host, pastes the host clipboard for a viewer paste shortcut, and then restores the agent's selection. The session's half of that handoff is `SessionClipboard` in `src/bin/kwin-viewer.rs`, shared by the local viewer and the remote frame sender. The host clipboard is always the one of the desktop the viewer window is on, which is the desktop of the server that received the call.

For remote MCP use, set the client's stdio command to SSH and run `kwin-mcp --no-viewer` on the remote host. SSH carries MCP messages. Alternatively `kwin-mcp --listen ADDRESS[:PORT]` on a machine serves other machines' servers over WebSocket (`src/remote.rs`; shared secret in `~/.config/kwin-mcp/remote-secret`), and `session_start` `host` starts a session there: the local `SessionRouter` forwards every call with that ID over the socket, and the listener gives each connection its own router, whose sessions it shuts down when the connection ends. A server that re-executes itself keeps those connections, and the listener is not involved: `RemoteSessions::hold` waits out every request to a listener, `remote::Handover::hold` stops each control socket once its byte counts show no part of a WebSocket message in the library's buffers, the socket's descriptor is inherited through the reload state together with the session-to-host map and the viewer PIDs, and `remote::adopt_control` continues on it without a handshake. The descriptor loses close-on-exec only in the exec call's `pre_exec`, and only when the target binary contains `remote::ADOPTS_CONTROL_MARK`, because a child or an older build holding the socket would keep sessions alive that nobody reaches; a server that dies hands nothing over, so its sessions still end at once. `viewer_open` on such a session opens the window on the caller's machine: the local router starts `kwin-viewer --stream`, which opens a second WebSocket (`/frames`, same secret) with a one-time ticket, and forwards `viewer_open` with that ticket on the control socket; the listener's `FrameSockets` pairs the two and hands the socket as stdin to `kwin-viewer --stream-serve` beside the session, which is that session's `viewer_child`. `src/viewer_stream.rs` holds the wire format and the sender's decisions, which put colour accuracy first and have no frame-rate target: a frame only when the pixels changed, the newest capture only and one frame on its way at a time, area-scaled to the viewer's reported drawable size, on a socket the kernel paces to 90% of the link speed (`--link-mbps` overrides it, loopback is unlimited). `ModeControl` sends raw RGB, the session's exact pixels, while the measured link carries a frame within 100 ms; it sends DSC only when raw is slower than that and DSC, with its measured encode time, arrives at least a quarter sooner, at the highest whole rate from 6 to 12 bpp the link carries in 100 ms (the rate follows the link, never the CPU), and a change of mode or rate needs 4 frames in a row. `Settle` sends a still DSC frame once more raw after 150 ms, and the viewer presents through a UNORM sRGB swapchain without conversion, so a still screen is pixel-exact. Viewer input returns on the frame socket; screenshots and all tool calls stay on the control socket. The remote viewer bridges the clipboard over the same frame socket: `--stream` owns the host half (the caller's desktop clipboard) and `--stream-serve` the session half. A paste shortcut sends `Request::ClipboardPaste` with the caller's clipboard text ahead of the key record, a copy or cut shortcut sends `Request::ClipboardCopy` and the sender answers with `Notice::Clipboard` once the session's selection changed; the sender handles each request before it reads the next record, and restores the agent's selection afterwards. These are JSON text messages carrying UTF-8 text of at most 1 MiB (`CLIPBOARD_TEXT_BYTES`; longer or non-text selections are refused whole, and a refused paste inserts nothing rather than the agent's selection). The sender announces the bridge in `hello` (`clipboard_text_bytes`), a viewer sends requests only to a sender that did, older senders ignore text messages and both ends ignore unknown text types, so either end may be older. `ClipText` has no `Display` and a redacted `Debug`, and `Request::decode`/`Notice::decode` never report the parser's message, so clipboard text reaches no log. The frame socket is plain `ws://`: clipboard text crosses the LAN unencrypted. A frame socket is bound to one session by its ticket and to one window, a viewer accepts a `clipboard` text only as the answer to its own last copy request, and the sender never answers with a selection that carries the generated-secret marker, so a viewer bridges its own session only. `clipboard_write target=host` for a remote session is carried out by the calling server's `SessionRouter::write_callers_clipboard` and never forwarded: text and generated secrets are made and written on the caller's machine and cross the network only in a viewer paste. `target=session` is forwarded, and a secret for it is generated by the listener on the session's machine, so only its parameters and its length cross the control socket. A listener refuses `target=host` from a peer. The capture ends with either socket. The remote host needs KDE, bubblewrap, render and input devices, and an active user D-Bus.
